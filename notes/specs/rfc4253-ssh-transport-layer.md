> 中核 5 本の全体像は [[ssh-core-rfcs]]（地図）を参照。本ノートは RFC 4253 単体の精読。
> **本研究にとっては、client の Evidence をセッションに束縛するための値（exchange hash H / session identifier）と、能力交渉の仕組みを提供する層。** クライアント認証そのものは [[rfc4252-ssh-authentication-protocol]] 側で行われる。

## 何を規定しているか

SSH のトランスポート層（2006-01、T. Ylonen / C. Lonvick (Ed.)）。**サーバ認証**、機密性、完全性、前方秘匿性を提供する。バイナリパケット形式、アルゴリズム交渉、Diffie-Hellman 鍵交換、鍵の導出、鍵の再交換、サービス要求を規定する。

**ホスト鍵の所持証明が行われるのはここ。** RFC 4251 §4.1 が述べる TOFU の実行場所（サーバー認証側。本研究の対象ではない）。本研究にとって重要なのは、ここで決まる exchange hash H と session identifier。

## 本研究に効く定義・要件

### §8 鍵交換と exchange hash H — 束縛点の全て

DH 鍵交換の実体。サーバは共有秘密 K を計算したうえで、次を連結してハッシュした **exchange hash H** を作り、**ホスト秘密鍵で H に署名**する:

```
H = HASH( V_C || V_S || I_C || I_S || K_S || e || f || K )
```

| 要素 | 内容 |
|---|---|
| `V_C` / `V_S` | クライアント／サーバの識別文字列（CR LF を除く） |
| `I_C` / `I_S` | クライアント／サーバの `SSH_MSG_KEXINIT` のペイロード**全体** |
| `K_S` | サーバの公開ホスト鍵（証明書を含みうる） |
| `e` / `f` | DH の交換値 |
| `K` | 共有秘密 |

サーバは `SSH_MSG_KEXDH_REPLY` で `(K_S, f, H への署名)` を返す。クライアントは §8 step 3 で `K_S` が本当に S のホスト鍵か検証する——**が、仕様はここでこう書く**:

> C is also allowed to accept the key without verification; however, doing so will render the protocol insecure against active attacks (but may be desirable for practical reasons in the short term in many environments). — §8, step 3

**TOFU の実行地点はこの一行。** RFC 4251 §4.1 が方針として述べたことが、ここで手続きとして現れる。

**`I_C` / `I_S` が H に入っていることが決定的に重要。** `SSH_MSG_KEXINIT` のペイロード全体がハッシュに含まれるので、**交渉内容の改竄はホスト鍵署名で守られる**。attestation の能力交渉を KEXINIT のアルゴリズム名リストに載せれば、それも自動的に H に束縛される（ダウングレード攻撃への耐性がタダで手に入る）。

### §7.2 session identifier — チャネル束縛の正規の穴

> The exchange hash H from the first key exchange is additionally used as the session identifier, which is a unique identifier for this connection. It is used by authentication methods as a part of the data that is signed as a proof of possession of a private key. Once computed, the session identifier is not changed, even if keys are later re-exchanged. — §7.2

つまり:

- session identifier = **最初の** KEX の exchange hash H
- **ユーザ認証の署名対象に必ず含まれる**（[[rfc4252-ssh-authentication-protocol]] §7 を参照）
- rekey しても**変わらない**

**これが SSH における channel binding の既製の仕組み**。attestation Evidence を session identifier に束縛すれば、Evidence がこの接続のために作られたことを示せる。

### §7 explicit / implicit サーバ認証

鍵交換方式は 2 種類に分類される:

- **explicit server authentication**: 鍵交換メッセージにサーバの真正性の証明（署名等）が含まれる
- **implicit server authentication**: サーバが共有秘密 K を知っていることを、メッセージと MAC で示すことで真正性を証明する

本文書が定義する DH 方式は explicit。ただし **implicit 方式を使ってもよい (MAY)** と明記され、その場合クライアントはサービス要求への応答を待ってからデータを送らねばならない。**新しい KEX 方式を定義する余地が仕様レベルで開いている**ことの根拠。

### §7.1 アルゴリズム交渉と cookie — 能力交渉と、予測不能性の供給源

`SSH_MSG_KEXINIT`（番号 20）で双方が name-list を送り合う。KEX 方式、ホスト鍵アルゴリズム、暗号、MAC、圧縮、言語をそれぞれ交渉する。相手の推測が外れた場合の扱い（optimistically sent packet を無視して正しい初期パケットを送り直す）も規定されている。

パケット形式の 2 番目のフィールドが本研究に効く:

```
byte         SSH_MSG_KEXINIT
byte[16]     cookie (random bytes)
name-list    kex_algorithms
...
```

> The 'cookie' MUST be a random value generated by the sender. **Its purpose is to make it impossible for either side to fully determine the keys and the session identifier.** — §7.1

**双方が 16 バイトのランダム値を必ず送り、その目的が「どちらの側も鍵と session identifier を完全には決められないようにすること」だと明記されている。** cookie は KEXINIT のペイロード（`I_C` / `I_S`）の一部なので、そのまま exchange hash H に入る。つまり **H には設計上、サーバ側の予測不能な寄与が必ず含まれる**。

### §6.6 公開鍵アルゴリズムの枠組み

> This protocol has been designed to operate with almost any public key format, encoding, and algorithm (signature and/or encryption). — §6.6

鍵型を定義する要素は 3 つ: 鍵形式（**証明書を含んでよい**）、署名／暗号アルゴリズム、署名のエンコーディング。公開鍵／証明書のエンコードは:

```
string    certificate or public key format identifier
byte[n]   key/certificate data
```

> The certificate part may be a zero length string, but a public key is required. [...] The certificate sequence contained in the certificate blob can be used to provide authorization. — §6.6

**「鍵 blob に証明書列を入れて authorization に使ってよい」と仕様が明示している。** OpenSSH の証明書も [[draft-ietf-sshm-cert]] もこの穴を使っている。attestation 情報を鍵 blob 側に載せる設計（Evidence や Attestation Result を証明書として運ぶ）もこの枠内に収まりうる。

### §6.1 パケットサイズ — Evidence を運べるか

全実装は**非圧縮ペイロード 32768 バイト以下、パケット全体 35000 バイト以下**を処理できなければならない (MUST)。さらに:

> Implementations SHOULD support longer packets, where they might be needed. For example, if an implementation wants to send a very large number of certificates, the larger packets MAY be sent if the identification string indicates that the other party is able to process them. — §6.1

**「大量の証明書を送りたい場合」が長大パケットの例として名指しされている。** TPM Quote（数百バイト）は余裕。問題は**イベントログ**（UEFI/IMA のログは数十 KB〜数 MB になりうる）で、32768 バイトに収まらない可能性が高い。分割送信か、ログを送らず PCR 値だけで済ませる設計かの判断が要る。

### §9 鍵の再交換

どちらの側からでも `SSH_MSG_KEXINIT` を送れば再交換が始まる。**ホスト鍵も変えてよい**。session identifier だけは変わらない。推奨頻度は 1GB 送信ごと、または 1 時間ごとのいずれか早いほう。

**接続中の再 attestation の受け皿になりうる**——RATS の streaming / 定期的な再検証を SSH に載せるなら、rekey に相乗りするのが自然。ただし「公開鍵演算なので頻繁にやるべきでない」と仕様が釘を刺している。

### §11.4 未知メッセージの扱い — 段階的導入の土台

> An implementation MUST respond to all unrecognized messages with an SSH_MSG_UNIMPLEMENTED message in the order in which the messages were received. Such messages MUST be otherwise ignored. — §11.4

**知らないメッセージは無視して `SSH_MSG_UNIMPLEMENTED` を返すだけ**。接続は壊れない。これが問い 2（後方互換性）の技術的な根拠になる。

## 拡張点・自由度

- **新しい KEX 方式を定義できる**（§7 が implicit 認証方式の使用を明示的に許す。番号 30–49 は方式固有 → [[rfc4250-ssh-assigned-numbers]]）
- **新しい公開鍵アルゴリズム／鍵形式を定義できる**（§6.6 が「ほぼあらゆる公開鍵形式で動くよう設計した」と述べる。証明書を含めてよい）
- ホスト鍵の検証方法は規定されない（§8 step 3 は「証明書またはローカル DB を使う、例えば」としか言わない）
- パケット長は 32768/35000 を超えてよい（相手の識別文字列で能力が分かる場合）

## 自研究との関係

（※ここは解釈）

**問い 4（freshness）に対する SSH 側の材料が出そろった。** RATS の Challenge/Response モデル（→ [[draft-ietf-rats-reference-interaction-models]]）が要求するのは「Verifier が生成した Handle が Evidence に暗号的に束縛されていること」。SSH が既に持っている束縛点は 2 つある:

| 束縛点 | 性質 | attestation への使い方 |
|---|---|---|
| **exchange hash H** | 毎回の KEX で新しく計算される。`I_C`/`I_S`（KEXINIT 全体）と `e`/`f`（両者の寄与）を含む | KEXINIT に nonce を載せれば H に入る。**サーバとクライアント双方の寄与が入るので、片側だけで値を決められない** |
| **session identifier**（最初の H） | 接続を通じて不変。ユーザ認証の署名対象に必ず入る | 認証層で Evidence を出す場合、これに束縛すれば接続に紐づく |

**ただし [[draft-ietf-rats-reference-interaction-models]] §2.2 の警告を思い出すこと。** あの節は「TLS nonce は Handle ではない」と切り分けている。H や session identifier は TLS nonce と同じく**鍵交換由来の値**であり、そのまま attestation nonce として使ってよいとは仕様上どこにも書かれていない。少なくとも次の 2 点は論証が要る:

1. **Verifier（＝本研究ではサーバー）の寄与が入っているか。** → **入る。§7.1 の cookie がまさにそれ**。サーバの KEXINIT に含まれる 16 バイトのランダム値が `I_S` 経由で H に入り、しかも仕様がその目的を「どちらの側も session identifier を完全には決められないようにするため」と明言している。**「Verifier が予測不能な値を寄与する」という Challenge/Response の要件を、SSH は最初から満たしている**
2. **TPM が署名できる形か。** → **条件付きで合う（2026-09-15 訂正）。** TPM 2.0 の `qualifyingData` の上限は「2 オクテット + その TPM が実装する最長ダイジェスト長」（→ [[tcg-tpm2-library-v185]]）。H の長さは KEX 方式名のハッシュで決まるので、`-sha256` 系の 32 オクテットならどの TPM でも入るが、**`-sha512` 系の 64 オクテットは SHA-512 を実装しない TPM には入らない**。H をそのまま渡すのではなく、ハッシュし直して正規化する設計が安全

**つまり「H（または session identifier）を TPM の qualifying data に渡して Quote を取る」設計は、材料の上では成立する。** 残る論点は「SSH の cookie が RATS の言う Handle の要件（推測困難性、Verifier による生成、リプレイ防止）を満たすと論証できるか」であって、そこが本研究の設計上の主張になる。参照モデルからの delta として明示すべき箇所。

**注意すべき差分が 1 つある。** cookie の仕様上の目的は「どちらの側も鍵を完全に決められないようにすること」であって、「Evidence の鮮度を証明すること」ではない。RATS 的には Handle は Verifier が freshness のために発行するものだが、SSH の cookie は**双方が対称に出す**。本研究がこれを Handle として使うなら、「サーバ側 cookie のみを Handle とみなす」のか「H 全体を Handle とみなす」のかを決め、その選択の妥当性を示す必要がある。

**研究テーマ（server からの challenge / client からの response）に照らすと、H の役割は「challenge そのもの」より「セッション束縛値」と見るのが素直。** 研究テーマは server が challenge を明示的に送ることを求めている。したがって設計の基本形は:

```
qualifyingData = HASH( server の challenge (nonce) ‖ session identifier ‖ 文脈 )
```

のように、**freshness は server の challenge が担い、SSH セッションへの束縛は session identifier が担う**形になる（`qualifyingData` のサイズ上限により正規化が要ることは上の 2. を参照）。上で検討した「H 自体を Handle とみなす」は、challenge の往復を省く代替案として位置づけ直す。

> **2026-10-13 訂正: この式だけでは足りない。** [[draft-reddy-rats-key-binding]] §8.3 が、まさにこの「claims set をハッシュして既存の attestation インターフェースの challenge として渡す」構成を批判している。TPM は `qualifyingData` を一切解釈しないので（[[tcg-tpm2-library-v185]] Part 1 §28.4）、**改竄されたクライアントは TPM 外の鍵のハッシュを入れて正当な Quote を取れてしまう。** `TPM2_Quote()` が示すのは「指定 PCR の値」と「呼び出し元が渡した 32 バイト」だけであって、「この SSH 鍵が TPM 内にある」ことではない。
>
> **SSH 鍵が TPM 内にあることを示すには `TPM2_Certify()` が別途必要**になる。したがって設計は次の 3 点セットになる:
>
> | 目的 | 手段 |
> |---|---|
> | 端末の状態 + freshness | `TPM2_Quote()`（`qualifyingData` に server challenge と session identifier の正規化値） |
> | SSH 鍵が TPM 内にあること | **`TPM2_Certify()`** による鍵の証明 |
> | 鍵の所持証明 (PoP) | **`publickey` 認証の署名**（[[rfc4252-ssh-authentication-protocol]] §7） |
>
> 詳細は [[draft-reddy-rats-key-binding]] の「自研究との関係」。

**問い 1（どのレイヤか）について、この RFC から言えること。**

KEX 方式として定義する案の利点は残る:

- KEXINIT のアルゴリズム交渉がそのまま能力交渉になり、`I_C`/`I_S` 経由で H に束縛されるのでダウングレード耐性が付く
- メッセージ番号 30–49 が方式固有なので IANA 手続きが要らない
- 未対応の相手とは方式が合意されないだけで、接続は普通に成立する（§7.1）＝段階的導入が自然に成り立つ

しかし研究テーマとの整合では不利になる:

- KEX はクライアント認証より前に走る。**§8 の DH 手順にはサーバー側の署名しかなく、server が challenge を送って client が Evidence を返す往復が無い**。KEX に載せるならクライアント側の Evidence を運ぶメッセージを新設し、challenge は鍵交換の寄与（cookie、`f`）で代用することになる
- イベントログのサイズ（§6.1）と、鍵交換のレイテンシに TPM Quote 生成時間が乗ること（問い 5）

**server challenge / client response の往復を明示的に書ける位置は、ユーザ認証層の新方式**（→ [[rfc4252-ssh-authentication-protocol]]、方式固有メッセージ 60–79 で server が challenge を送れる）。本 RFC は、そこで使う session identifier と能力交渉（→ [[rfc8308-ssh-extension-negotiation]]）を提供する層として位置づけるのが、現在の研究テーマに合う。

**再 attestation は rekey（§9）に相乗りできる。** 長時間セッション中に状態が変わる問題（[[draft-ietf-rats-reference-interaction-models]] の Streaming が扱う領域）に対し、SSH には既に 1 時間ごとの鍵再交換という習慣がある。これに attestation を乗せれば、新しい仕組みを増やさずに継続的検証ができる。

## 未解決・気になる点

- cookie は「random value」とは規定されるが、**乱数源の質については §7.1 は何も言わない**（RFC 4251 §9.1 Pseudo-Random Number Generation が別途扱う）。attestation の freshness を cookie に依存させるなら、この節を精読して要求水準を確認すること
- 更新 RFC のうち **8332（rsa-sha2-*）、8709（ed25519）、9142（KEX 更新）** は現行実装の実態に直結する。未取得
- イベントログを 32768 バイトに収める方法（分割、圧縮、ログを送らず PCR 値のみ、ログは別チャネル）。**設計上の分岐点なので早めに詰める**
- §6.3 の暗号化と §6.4 の完全性は流し読み。attestation の設計には効かないと判断
- §8 の DH 手順に「クライアント側の Evidence」を足す形が RFC 4253 の枠内に収まるか、それとも別方式の新設になるかは要検討（KEX 案を代替として残す場合）
