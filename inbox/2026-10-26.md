## papers

- **[medium]** "TPM-Attest: Hardware-Rooted Integrity Attestation as a Kernel-Level Anti-Cheat Alternative for Linux" — Gedela, Yaswanth（GITAM University）, arXiv 2026-09-17 — <https://arxiv.org/abs/2609.20909>
  - Linux のゲームクライアントを Attester にして、TPM 2.0 + IMA の Evidence で「クリーンに起動し許可されたソフトだけが動いている」ことをサーバーに示す。**server nonce に束縛した fresh な TPM Quote を出せたときだけセッション参加を許可**し、IMA ログには duplicate-leaf 衝突に強い Merkle tree を使う。改竄セッション 500 件を全検出、実機で再 attestation は 3 秒未満、red-team で bypass 条件 2 件を特定（abstract による）。
  - （解釈）SSH ではないが、**クライアント → サーバー方向の challenge-response 型 attestation をセッション確立の可否判定に使う**という構図は本研究と同じ。レイテンシ（問い 5）と IMA ログの扱いの比較対象になる。arXiv 新着検索（`remote attestation TPM`）で発見。

## specs

- **[medium]** TCG Vulnerability Advisory TCGVRT0010 "TPM 2.0 Improper Object Slot Reuse"（CVE-2026-6726）— TCG — <https://trustedcomputinggroup.org/wp-content/uploads/VRT0010-Advisory_Final-1.pdf>（NVD 系: <https://app.opencve.io/cve/CVE-2026-6726>）
  - TPM 2.0 リファレンスコード（Library **v184 まで**）で、オブジェクト格納領域とハッシュコンテキスト領域の分離不足により、特権を持つローカル攻撃者が **TPM-aware CA に偽の鍵に対する credential を発行させ、以後の attestation を偽造できる**。影響対象として AK・DevID 鍵・TLS 認証鍵が挙がる。CVSS v3.1 7.9 / v4.0 8.5（検索スニペットによる。advisory PDF は 404 で一次未読）。
  - （解釈）`docs/scope.md` の CVE 除外条件の例外（attestation の信頼の根を崩すもの）に当たる。**AK を CA で登録する設計（Verifier 配置・問い 3）の脅威として Security Considerations で言及しうる。** 既存ノート `notes/specs/tcg-tpm2-library-v185.md` の版（v185）が修正版に当たるかは未確認。
- **[low]** "Epoch Markers" — `draft-ietf-rats-epoch-markers-06`, 2026-10-20 — <https://datatracker.ietf.org/doc/draft-ietf-rats-epoch-markers/>
  - 既読 `-05` の改訂。freshness の手段（問い 4）として challenge-response と対比するときの参照先。差分は未確認。

その他: SSHM（WG 文書・Related 欄とも）と SEAT は全件既読。RATS Related 欄の新規は `draft-watts-rats-verification-promotion-appraisal-00`（2026-10-21, AI エージェントの assurance profile）だけで、AI 系として除外。IANA SSH Parameters は最終更新 2026-09-08 のままで変化なし。

### メーリングリストの観察

- **`ssh@ietf.org`**: 前回以降の新着は IETF 127 のセッション確定通知（10-23）のみ。attestation 関連なし。
- **`seat@ietf.org`**: "Properties rewrite in use-cases draft"（Ionut Mihalcea 発起、10-21〜25、長スレッド）、"Architectural considerations in attested TLS"（10-23）、"Provisioning cryptographic identity for guest VMs"（Ritz, 10-21）、IETF 127 アジェンダ募集。件名に SSH の言及は依然なし。use-cases draft の properties 書き直しは次版（`-02`）で反映されるはずなので、そのときに差分を見ること。
- **`rats@ietf.org`**: **"Request for cryptographic review: proving that a key was created by one specific TPM, and pinning one anchor per TPM"**（Chris Drake, 2026-10-24）— <https://mailarchive.ietf.org/arch/msg/rats/shXQXLn4OqjPnEhRiTqZqqb-Khk/>
  - EK に暗号化した salt で salted HMAC セッションを張り、Registrar が組み立てた `TPM2_CreatePrimary` を 2 本（決定的な anchor 鍵と AK）通させて、**応答 HMAC で「その鍵はその EK を持つ TPM が作った」ことを示す**方式への暗号レビュー依頼。credential activation を使わず、管理者権限も永続スロットも要らないのが売り。用途は AI エージェント／ロボットの ID 登録（`draft-drake-agent-identity-registry-04`）で SSH には触れていない。
  - （解釈）**SSH 鍵が TPM 内にあることを示す key residency の別解**で、`draft-reddy-rats-key-binding`（→ `notes/specs/draft-reddy-rats-key-binding.md`）の比較材料になる。レビュー結果（特に Q1 の OAEP padding oracle）次第なので、スレッドの続きを追う。
  - 他は epoch-markers-06 の告知、IETF 127 セッション、ounsworth privacy framework へのフィードバック。

## impl

- **[medium]** attezt — Morten Linderud（Foxboron）— <https://pkg.go.dev/github.com/foxboron/attezt>（リポジトリ: <https://github.com/foxboron/attezt>、解説ブログ 2026-03-21: <https://linderud.dev/blog/acme-device-attestation-smallstep-and-pkcs11-attezt/>）
  - ACME の `device-attest-01` チャレンジで Linux 端末に TPM ベースの device certificate を発行する remote attestation ツール群。Attestation CA（`atteztd`）とクライアントエージェント（`attezt-agent`、TPM 証明書を PKCS#11 エージェント経由で提供）からなる。作者はこれで step-ca に SSH 証明書を署名させる構想をブログで述べている（検索スニペットによる。ブログ本文は WebFetch 権限拒否、GitHub API は 403 で未読）。
  - （解釈）既読 `ssh-tpm-ca-authority`（→ `notes/impl/ssh-tpm-ca-authority-device-attested-certs.md`）と同じ作者による後継的な系統。**「attestation は CA 発行時に 1 回だけ行い、SSH 接続時には証明書を見るだけ」という CA 兼務型 Verifier（問い 3）**の実装例として、毎接続 challenge-response する本研究の設計と対比できる。ノート化は一次情報を読めてから判断する。
